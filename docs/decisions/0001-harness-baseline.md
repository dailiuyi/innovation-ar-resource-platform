# 0001：基础 Harness 的范围与证据规则

日期：2026-09-17。状态：采纳。维护责任：修改开发/验证工作流的贡献者，变更由项目负责人审查。

## 决定

在现有仓库增加轻量 Python 验证入口、知识导航和跨会话任务模板。复用已存在的契约、构建、浏览器和入库验收；命令失败、阻塞与未执行分别报告。所有日常运行证据放入独立忽略目录，关联当前源码指纹。

入库验收先在本次目录构建当前后端源码；不覆盖日常 Demo 的 Jar，不依赖已有产物代表当前代码。默认不接自动修复、模型调度、合并、部署或业务后台任务队列。

## 原因与影响

已有多种验证脚本，但报告输出、环境要求和副作用并不统一。先提供可重复的验证与可恢复交接，比增加 Agent 数量更容易明确完成依据。独立构建会增加磁盘和构建成本，换来不干扰日常环境及清晰的产物来源。

## 后续状态

上述构建与 Windows 约束保留当时决策背景，不是当前启动步骤。现行 ingestion 复用由 `scripts/check_java.py --package` 测试通过的同源码 Jar，不再自行构建；Linux 入库/真实样包另走固定隔离 Compose 实例，见 [Harness](../13-harness.md)。Windows profile 与 Linux 流程的证据不能相互冒充。

## 重新考虑条件

多人协作需要强制合并门槛时，可把同一入口接到受支持的 CI 运行环境；跨会话人工恢复出现稳定重复成本时，再考虑任务状态自动化。新增 profile 必须明确隔离方式和证据范围。Linux 入库支持需要先移除现有 Windows 运行时约定并实际验证，不能只改 doctor 条件。
